# ADR 0004: Configure Native Next.js Foundations

## Status
Accepted

## Date
2026-11-10

## Context
Following the baseline CLI scaffolding ([ADR 0003](0003-create-next-app.md)), the project requires completing essential framework configurations before building product features.

To avoid premature abstraction and over-engineering, we prioritize canonical, native Next.js 16 patterns and direct framework APIs. We explicitly avoid introducing artificial wrappers, custom facades, or home-grown utility layers where standard framework idioms suffice.

This ADR establishes the native foundational configuration for:
- Asynchronous route segment and context typings (`PageProps`, `LayoutProps`, `RouteContext` via `next typegen`).
- Top-level routing resiliency boundaries (`global-error.tsx`, `error.tsx`, `not-found.tsx`, `loading.tsx`).
- Private folder conventions and route-level component colocation (`src/app/**/_components/`).
- Universal client-side navigation using native `next/link`.
- Lightweight infrastructure health probe via standard Route Handler (`src/app/api/health/route.ts`).
- Server and client observability via native `instrumentation.ts` and `instrumentation-client.ts`.
- Node.js Proxy request interception and security headers via native Next.js 16 `src/proxy.ts`.
- Clear React Server Component (RSC) vs. Client Component boundaries and asynchronous rules.
- Native declarative caching architecture (`'use cache'`, `cacheLife`, `cacheTag`).
- Dynamic request boundary and prerender opt-out via `connection()`.
- Post-response background execution via native `after()`.
- Standard file-based metadata, SEO, and web manifest conventions (`robots.ts`, `sitemap.ts`, `manifest.ts`).
- Server Actions and React 19 mutation paradigms (`'use server'`, `useActionState`, `useOptimistic`).

## Decision

We establish thirteen native Next.js 16 configuration and architectural layers:

---

### 1. Native Route Segment & Context Typings (`next typegen`)

Next.js generates global route-aware helpers. Do **not** manually redeclare `PageProps`, `LayoutProps`, or `RouteContext` interfaces. Route `params` and page `searchParams` are Promises in Next.js 16.

```tsx
// src/app/page.tsx: route-aware type generated by Next.js
export default function Page(_props: PageProps<"/">) {
  return <main>Home</main>;
}
```

```tsx
// src/app/layout.tsx
export default function Layout({ children }: LayoutProps<"/">) {
  return <html lang="en"><body>{children}</body></html>;
}
```

```ts
// src/app/api/health/route.ts
import { NextResponse } from "next/server";

export function GET(_request: Request, _context: RouteContext<"/api/health">) {
  return NextResponse.json({ status: "ok" });
}
```

These examples demonstrate the type helpers, not a request to rewrite existing file signatures. Continue running `next typegen && tsc --noEmit` via `pnpm typecheck`.

### 2. Native Error Boundaries & Fallback Hierarchy (`src/app/`)

- **Route-Level Boundaries (`src/app/error.tsx` & `src/app/global-error.tsx`)**:
  - **Explicit Props Contracts (`ErrorBoundaryProps`, `GlobalErrorProps`)**: Anonymous inline prop type literals (`{ error: ...; reset: ... }`) are prohibited. Both boundaries declare and export named, strongly-typed interfaces with `readonly` fields:
    ```tsx
    export interface ErrorBoundaryProps {
      readonly error: Error & { digest?: string };
      readonly reset: () => void;
    }

    export interface GlobalErrorProps extends ComponentProps<"html"> {
      readonly error: Error & { digest?: string };
      readonly reset: () => void;
    }
    ```
  - **`src/app/error.tsx`** is a Client Component for route-segment errors, accepting `ErrorBoundaryProps`.
  - **`src/app/global-error.tsx`** handles root-layout failures, accepts `GlobalErrorProps`, and renders its own `<html>` and `<body>`. Extending `ComponentProps<"html">` allows optional root HTML attributes (`lang`, `dir`, `className`) to be forwarded to the document root while strictly enforcing the Next.js `{ error, reset }` contract.
  - Both components show a generic user-facing message and a recovery button. They must **not** render `error.message` or other internal details. Errors are captured separately by server-side instrumentation where applicable.
- **`src/app/not-found.tsx`** provides a navigable 404 fallback via native `next/link`.
- **`src/app/loading.tsx`** provides the native Suspense fallback. A loading UI alone does not implement network timeouts or bounded retries.
- **Component-Level Boundaries via Native `catchError` (`next/error`)**:
  - For granular error recovery at the component level (e.g., isolating widgets, tabs, or third-party interactive panels without crashing the entire route segment), Next.js provides the native `catchError` Higher-Order Component (HOC) and `type ErrorInfo` via `import { catchError, type ErrorInfo } from "next/error"`.
  - **Module Disambiguation (`next/error`)**:
    - The **default export** (`import Error from "next/error"`) is legacy and restricted to the Pages Router (`pages/_error.js`). It must **not** be used in App Router code.
    - The **named exports** (`catchError` and `type ErrorInfo`) are modern, native, and stable in Next.js 16 (`v16.3.0+`, stabilized from `unstable_catchError` introduced in `v16.2.0`).
    - `catchError` provides native Next.js integration out of the box: `retry()` re-renders within a React 19 `startTransition` while preserving outside Client Component state, framework flow-control exceptions (`redirect()`, `notFound()`) are seamlessly forwarded without being caught, and error state automatically clears upon client-side navigation.
    - Standardizing on `catchError` eliminates any requirement for manual React class error boundaries (`componentDidCatch`) or external packages (such as `react-error-boundary`).
- **Not adopted:** root `default.tsx`, because the application has no parallel route slots (`@slot`).

Current runtime components are independently tested where appropriate; see [ADR 0005](0005-production-baseline-and-testing.md).

### 3. App Router Private Folders & Component Colocation (`src/app/**/_components/`)

Next.js App Router treats all folders within `src/app/` as potential route segments by default unless prefixed with an underscore (`_`). To colocate private components, client boundaries, and UI logic alongside route entry points without exposing them to public URL routing:

- **Private Folder Convention (`_folder`)**:
  - Folders prefixed with `_` (such as `src/app/_components/` or nested `src/app/<segment>/_components/`) opt out of URL routing.
  - Files and subfolders inside private folders are completely ignored by the Next.js routing system and will not match any browser URL path.
- **Locality and Thin Route Handlers**:
  - Route entry points (`page.tsx`, `layout.tsx`) remain thin presentation layers.
  - Route-specific components, private hooks (`_hooks/`), and client boundaries (such as `web-vitals.tsx`) are colocated in private folders directly adjacent to their consumers.
- **Scope Distinction**:
  - **`src/app/**/_components/`**: Private, route-specific components not meant for global consumption across disparate domains.
  - **`src/components/`**: Cross-cutting, shared application UI components and design system primitives.

### 4. Native Navigation via `next/link`

All internal navigation must use Next.js's native `Link` component (`import Link from "next/link"`):

- **Rule**: Never use raw HTML `<a>` tags for internal paths (`/`, `/dashboard`, `/login`). Raw `<a>` tags force full page reloads, drop React state, and bypass Partial Prerendering (PPR) prefetch caches.
- **Prefetching**: When using `next/link`, Next.js automatically prefetches route chunks in the viewport during idle time, delivering instant page transitions.
- **External Links**: Only external destinations use standard `<a>` tags with `target="_blank"` and `rel="noopener noreferrer"`. Upstream Next.js guidance (`errors/invalid-href-passed.mdx`) and Context7 audits confirm that `next/link` is strictly for internal routes; passing external URLs triggers warnings and unexpected behavior. Furthermore, the official `no-html-link-for-pages` ESLint rule explicitly ignores outbound URLs (`https://`), establishing plain `<a>` as the sanctioned element for external links.

  _request?: NextRequest,
  _context?: RouteContext<"/api/health">

### 6. Native Lifecycle Instrumentation (`instrumentation.ts` & `instrumentation-client.ts`)

We leverage native Next.js observability hooks without adding proprietary wrapper packages:

- **Server Instrumentation (`src/instrumentation.ts`)**:
  - Implements `register()` for server startup initialization.
  - Implements `onRequestError` (Next.js 15+ native hook) to log unhandled server errors with structured metadata (`path`, `method`, `digest`):
  ```ts
  import type { Instrumentation } from "next";

  export async function register() {
    // Server startup hook
  }

  export const onRequestError: Instrumentation.onRequestError = async (
    err,
    request,
    context
  ) => {
    console.error(
      JSON.stringify({
        severity: "ERROR",
        event: "next_request_error",
        message: err instanceof Error ? err.message : String(err),
        digest: (err as { digest?: string }).digest,
        path: request.path,
        method: request.method,
        routerKind: context.routerKind,
        routeType: context.routeType,
      })
    );
  };
  ```

- **Client Runtime Hook (`src/instrumentation-client.ts`)**:
  - Observes client-side App Router navigations ahead of hydration via `onRouterTransitionStart`:
  ```ts
  export function onRouterTransitionStart(
    url: string,
    navigationType: "push" | "replace" | "traverse"
  ) {
    // Client-side route transition hook
  }
  ```

### 7. Native Node.js Proxy (`src/proxy.ts`)

In Next.js 16, `proxy.ts` replaces the former `middleware.ts` naming convention and executes in the **Node.js runtime by default**, not Edge. It runs before matched routes and can set response headers, redirect, or rewrite requests.

The existing implementation sets `X-Frame-Options`, `X-Content-Type-Options`, and `Referrer-Policy` and deliberately excludes selected static resources from its matcher. This is not an authentication boundary. Authorization must be enforced independently in protected server routes and actions.

Proxy should stay lightweight and should not perform slow data fetching. There is no framework-guaranteed fixed execution budget such as "under 10 ms". See https://nextjs.org/docs/app/api-reference/file-conventions/proxy.

### 8. Server vs. Client Component Boundaries & Asynchronous Rules

Next.js 16 and React 19 enforce clear architectural boundaries between Server Components (RSC) and Client Components:

- **Default to React Server Components (RSC)**:
  - All components within `src/app/` are Server Components by default without any directive.
  - They render strictly on the server, contribute 0 bytes to the client JavaScript bundle, and can access backend resources (database, filesystem, secure environment variables) directly.
- **Strict `'use client'` Directive Rules**:
  - The `'use client'` directive defines a boundary where server-rendered markup becomes interactive on the client.
  - Mark a component with `'use client'` **strictly** when it requires:
    1. Interactive state or reducers (`useState`, `useReducer`, `useActionState`).
    2. Lifecycle side-effects (`useEffect`, `useLayoutEffect`).
    3. Browser DOM event listeners (`onClick`, `onChange`, `onSubmit`).
    4. Direct browser APIs (`window`, `localStorage`, `navigator`, `document`).
    5. React Context consumers or custom interactive hooks (`useReportWebVitals`, `usePathname`).
  - Keep client boundaries as leaf components at the bottom of the component tree to maximize server-side rendering.
- **Asynchronous Component Constraints**:
  - **Server Components**: Can and should be `async` functions whenever awaiting promises, fetching data, or consuming asynchronous route context:
    ```tsx
    export default async function Page(props: PageProps<"/">) {
      const params = await props.params;
      const searchParams = await props.searchParams;
      return <main>{/* rendered server content */}</main>;
    }
    ```
  - **Client Components**: **MUST NEVER** be declared as `async` functions (React does not support async client components and will throw runtime errors). To consume asynchronous data or Promises inside a Client Component, pass the Promise from a parent Server Component and read it using React 19's `use(promise)` within a `<Suspense>` boundary, or fetch via client event handlers:
    ```tsx
    "use client";
    import { use } from "react";

    export function ClientWidget({ dataPromise }: { readonly dataPromise: Promise<string> }) {
      const data = use(dataPromise);
      return <div>{data}</div>;
    }
    ```
  - **Asynchronous Route Context in Next.js 16**: `params` and `searchParams` are asynchronous `Promise`s across all App Router entry points. They must always be awaited in Server Components (`await props.params`) or resolved with `useParams()` / `useSearchParams()` from `next/navigation` in Client Components.

### 9. Native Declarative Caching Architecture (`'use cache'`, `cacheLife`, `cacheTag`)

With Next.js 16 Cache Components enabled (`cacheComponents: true` in `next.config.ts`), we replace legacy `unstable_cache` and manual `fetch` caching options with the native `'use cache'` directive:

- **Directive Placement**:
  - **File level**: Placing `'use cache'` at the top of a file caches all exported functions and components.
  - **Component level**: Placing `'use cache'` at the top of a React Server Component caches its rendered output tree.
  - **Function level**: Placing `'use cache'` at the top of an exported async function caches its serialized return value.
- **Mandatory Async Rule**:
  - Any function or component that declares `'use cache'` **must be async**.
- **Isolation of Dynamic Request Data**:
  - Cached scopes cannot read request-time dynamic APIs (`cookies()`, `headers()`). Read cookies, authentication sessions, or headers outside the cached boundary and pass explicit primitives as arguments:
  ```tsx
  import { cacheLife, cacheTag } from "next/cache";

  export async function getCachedExamSummary(examId: string) {
    "use cache";
    cacheLife("hours");
    cacheTag(`exam-${examId}`, "exams");

    return await fetchExamDetails(examId);
  }
  ```
- **Semantic Tagging & Revalidation**:
  - Group cached data using `cacheTag(...)`.
  - Invalidate selectively in Server Actions or Route Handlers using native `revalidateTag(tag, "max")` or `updateTag(tag)` without forcing cold rebuilds of unrelated pages.

### 10. Dynamic Prerender Opt-Out & Request Boundaries (`connection()`)

In Next.js 16, components that require request-time execution without accessing cookies or headers must not rely on artificial dynamic hacks (such as reading dummy headers).

- Use the native `connection()` function from `'next/server'`:
  ```tsx
  import { connection } from "next/server";

  export async function RequestTimeBadge() {
    await connection(); // Signals to Next.js prerender to pause here; downstream code runs only at request time
    const timestamp = new Date().toISOString();
    return <span>{timestamp}</span>;
  }
  ```
- This allows parent layouts and sibling components to remain statically prerendered or cached under Partial Prerendering (PPR), while explicitly deferring only the required dynamic sub-tree to request time.

---

### 11. Native Post-Response Background Execution (`after()`)

For non-blocking side-effects that should not delay the user's HTTP response or Time to First Byte (TTFB), we standardize on native `after()` from `next/server`:

```tsx
import { after } from "next/server";

export async function submitExamAttemptAction(formData: FormData) {
  "use server";
  const result = await saveAttempt(formData);

  // Schedules telemetry, audit logging, or cache warming to run after the response is completed
  after(async () => {
    await emitAuditLog({ event: "exam_submitted", id: result.id });
  });

  return { success: true };
}
```

- Standardizing on `after()` eliminates external background queue dependencies for simple secondary logging and telemetry tasks.

### 12. Native File-Based Metadata, SEO & Manifest Conventions

We adopt Next.js 16 file-based metadata conventions to guarantee search engine discoverability and PWA readiness:

- **`src/app/robots.ts`**: Implements search crawler rules using typed `MetadataRoute.Robots`:
  ```ts
  import type { MetadataRoute } from "next";

  export default function robots(): MetadataRoute.Robots {
    return {
      rules: {
        userAgent: "*",
        allow: "/",
        disallow: ["/api/", "/_components/"],
      },
      sitemap: "https://example.com/sitemap.xml",
    };
  }
  ```
- **`src/app/sitemap.ts`**: Provides XML sitemaps using typed `MetadataRoute.Sitemap`.
- **`src/app/manifest.ts`**: Generates web application manifests using typed `MetadataRoute.Manifest`.
- **OpenGraph & Dynamic Images**: Colocated `opengraph-image.tsx` using native `ImageResponse` from `next/og`.

### 13. Server Actions & React 19 Mutation Patterns (`'use server'`)

For data mutations, form submissions, and state transitions, we enforce native React 19 Server Actions:

- **Location & Colocation**:
  - Global/shared actions reside in `src/actions/` or domain modules with the `'use server'` directive.
  - Route-specific actions reside in private folders (`src/app/**/_actions/`).
- **React 19 Hooks Integration**:
  - Interactive forms bind Server Actions via React 19's `useActionState` (replacing deprecated `useFormState`):
    ```tsx
    "use client";
    import { useActionState } from "react";
    import { submitAnswerAction } from "./_actions/submit";

    export function AnswerForm() {
      const [state, formAction, isPending] = useActionState(submitAnswerAction, null);
      return (
        <form action={formAction}>
          {/* form inputs */}
          <button type="submit" disabled={isPending}>Submit</button>
        </form>
      );
    }
    ```
  - Optimistic feedback uses React 19 `useOptimistic` to deliver instant client updates before server revalidation completes.

## Consequences

- **Positive**:
  - **Framework-First Simplicity**: Uses 100% native Next.js 16 APIs and conventions without custom wrapper layers or premature domain abstractions.
  - **Type-Safe Routing**: Full compile-time validation for asynchronous route parameters via `next typegen`.
  - **Predictable Rendering Model**: Unambiguous Server vs. Client component boundaries; no accidental bundling of backend code into client payloads.
  - **Unified Caching Strategy**: Native `'use cache'`, `cacheLife`, and `cacheTag` integrated with `cacheComponents: true` and Partial Prerendering (PPR).
  - **Precise Prerendering Control**: `await connection()` isolates dynamic branches without forcing entire pages into dynamic rendering.
  - **Non-blocking Telemetry**: `after()` offloads background processing without inflating server response times.
  - **Error recovery interface**: Root and route boundaries display generic messages and recovery buttons; timeouts and bounded retries are separate concerns.
  - **Clean Route Colocation**: Private folders (`_components/`, `_actions/`) prevent route clutter and unintended public URL endpoints while keeping route entry points thin and focused.
  - **Instant Navigation**: Standardized `next/link` usage leveraging Next.js Partial Prerendering (PPR) prefetching.
  - **Lifecycle hooks**: Server error capture is implemented; the client transition hook exists but does not yet report telemetry.
  - **Request Security Headers**: Baseline headers applied to requests matched by `src/proxy.ts`.
- **Negative / Operational**:
  - Dynamic route parameters must always be awaited (`await params`, `await searchParams`).
  - Client Components must never be async functions.
  - Cached functions must be async and cannot read request-time APIs directly.
  - Node.js Proxy should remain lightweight; do not use it as the sole authorization mechanism.
